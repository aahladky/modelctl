## Capability response (pre-sync, schema 2)

A **live** re-probe of `build-sycl/bin/llama-server --modelctl-capabilities`
in this session crashes during backend registry init:

```
terminate called after throwing an instance of 'sycl::_V1::exception'
what(): No device of requested type available.
  at dpct::dev_mgr::dev_mgr() -> sycl::detail::select_device()
```

This reproduced identically with `ONEAPI_DEVICE_SELECTOR` unset, and forced
to `level_zero:0`, `level_zero:1`, and `level_zero:0,1`, and independent of
sandboxing — so it was not a GPU permission or multi-GPU-selection issue
(`zello_world` enumerates the same devices via Level Zero directly without
error).

**Update, same day:** confirmed transient, not a real bug. A minimal raw
SYCL probe (`sycl::platform::get_platforms()`) in this same session
initially returned zero platforms too — the exact same symptom one layer
down, with `SYCL_UR_TRACE=-1` showing the Level-Zero V2 adapter loading
and correctly enumerating both GPUs on that traced run. Re-running the
plain probe (no trace var) afterwards succeeded consistently (3/3 runs),
and re-probing both `build-sycl/bin/llama-server --modelctl-capabilities`
(pre-sync) and the post-sync `build-sycl-sync` binary (see
`2026-07-30-impact-review.md` / Task 0.3) now succeed and return
**byte-for-byte identical** capability JSON. No `llama-server` process was
running at the time. Best explanation: first-process-in-a-while SYCL/UR
adapter cold-start flakiness in this session (plugin discovery or L0
context init racing on first touch), not a build/environment mismatch and
not anything the upstream sync caused or fixed. Treat as resolved for
baseline purposes; if it recurs, retry once before assuming a real
regression.

```bash
  --mmproj /home/aaron/models/unsloth/Qwen3.5-122B-A10B-GGUF/mmproj-F16.gguf \
  --cache-type-k q8_0 --cache-type-v q8_0
```

**Finding:** this generated `run.sh` still references the pre-move binary
path `/home/aaron/workspace/llama.cpp/build-sycl/...`, which no longer exists
after the repo was relocated to `~/workspace/moe-serving` (see commit
`51051b3`). The artifact was not regenerated after that move. This is a
pre-existing staleness bug independent of the upstream sync — flagged here,
not fixed, since regenerating artifacts (`modelctl regen`) restarts the live
router/Hermes sync and should not be done incidentally as a side effect of
freezing a baseline snapshot on a machine serving real traffic.
