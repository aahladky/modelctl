Full conflict-resolution rationale is in each commit's body (`git log
9b2a08881..sync/moe-cache-upstream-2026-07-30`) per the roadmap's Task 0.3
requirement. Summary of the highest-risk calls:

- **`ggml-backend.cpp`**: the impact review's flagged commit (`dee2a846b`,
  backend-selection logic) turned out to live in a different function
  (`ggml_backend_sched_backend_id_from_cur`) than the cache's hook point
  (`ggml_backend_sched_compute_splits`'s `copy_experts` lambda), which was
  byte-identical to the feature's original base. Applied verbatim — no real
  conflict existed despite the file-level risk ranking.
- **`ggml-sycl.cpp`**: same story for `efb3036c1` (fused top-k MoE) — it
  lives entirely in `ggml_backend_sycl_graph_compute_impl`'s dispatch loop
  and a new `topk-moe.cpp`, fusing the expert-*selection* chain
  (softmax→argsort→get_rows) that runs *before* `mul_mat_id`. Doesn't touch
  `ggml_sycl_mul_mat_id` or the scheduler copy path. Applied verbatim, but
  flagged: whether fusion-on vs. fusion-off produces the same `ids_tensor`
  content feeding the cache's hook is a real question for Task 0.6's
  correctness matrix (`GGML_SYCL_ENABLE_FUSION=0/1`), not resolvable by
  reading code alone.
- **`server-context.cpp`**: `ee3d1b54c` (common_memory abstraction) only
  touches slot-level KV seq_rm/seq_cp/seq_add — unrelated to the cache's
  phase hook and metrics/reset routes. Applied verbatim.
- **New, not flagged by the Task 0.2 review**: `c264f65ff` (CLI HTTP
  refactor) split `llama_server()` into two overloads in `server.cpp`
  itself (the review only connected it to the standalone `llama-cli` tool),
  introducing an `is_router_server` invariant. The cache's CLI-to-globals
  wiring is now gated on `!is_router_server` to keep it honest about that
  invariant, even though the wiring itself (plain memory writes) didn't
  strictly require it. **This is the one place the Task 0.2 risk ranking
  was wrong about *where* the blast radius landed** — `c264f65ff`'s impact
  on this feature is in `server.cpp` control flow, not `common/arg.cpp` as
  originally flagged (arg.cpp's actual 385-line drift turned out to be
  unrelated CLI/env-var churn that didn't touch either of the feature's two
  insertion points there).
- **Bonus fix**: `--moe-hybrid-mode`'s handler was missing the
  `__attribute__((weak))` guard every other MoE-cache extern in this feature
  uses (server.cpp, server-context.cpp) — the one exception would very
  likely have broken CPU-only linking. Fixed to match the established
  pattern.

## Live capability verification (beyond what the porting pass could confirm)

The SYCL device-selection crash noted in `2026-07-30-baseline.md` turned out
to be transient session flakiness, not a real bug (see that doc's update).
Once resolved, both binaries were re-probed directly:

```
diff <(pre-sync build-sycl --modelctl-capabilities) \
     <(post-sync build-sycl-sync --modelctl-capabilities)
# exit 0 — byte-for-byte identical
```

The ported feature reports the exact same schema-2 capability response
(`moe_weight_transfer_cache: true` on both SYCL0/SYCL1, `moe_hybrid_cpu_miss:
false`, all six CLI flags present, weak-symbol linkage confirmed via `nm`)
as the pre-sync baseline. This is a real, live signal — not just "it
compiles" — that the port preserved the feature's externally-observable
behavior across 348 commits of upstream drift, though it is **not** a
substitute for Task 0.6's deterministic correctness matrix (logits/token-ID
comparison under actual cache hit/miss/eviction paths), which still needs a
real model loaded.
